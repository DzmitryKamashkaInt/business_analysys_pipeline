## Findings

### 1. Architecture-direction conflict (headline finding)

The estimate and the confirmed architecture describe two structurally different backends, not the same backend described in different tech-stack vocabulary. The estimate's core assumption — a custom Spring Boot + JPA + PostgreSQL service that is itself the system of record for catalog (~11 tables, JSONB custom props), identity (custom JWT + 3-role RBAC: Admin/Editor/Viewer), and commerce (own order-number generation, address storage, order history table) — directly contradicts the confirmed architecture's central decision: **Bitrix24 is the system of record for identity, catalog, and orders/payment**, and the Starter backend is explicitly a thin bridge/sync/read-model layer around it (BR-4). Specific direct contradictions, not just framing differences:

- Estimate uses **Stripe**; confirmed scope explicitly requires checkout via **Bitrix24 Payment APIs** through a custom Rumica checkout form — not Stripe, not any other gateway.
- Estimate builds a **custom JWT + 3-role hierarchy (Admin/Editor/Viewer)**; confirmed architecture requires auth against **Bitrix24 identity (contacts)** via email/password + Google OAuth — explicitly not a custom JWT/RBAC system with its own role hierarchy — and the confirmed role model is Admin-only (catalog management), not three roles.
- Estimate builds a **persistent server-side cart with guest/user merge logic**; confirmed architecture's Key Architectural Decision #5 is explicitly the opposite: client-side cart, no dedicated cart-persistence service/table.
- Estimate builds **order creation/storage, order numbers, order history table**; confirmed architecture states orders are created as Bitrix24 CRM deals and "My Orders" is sourced **live** from Bitrix24, with no separate order database.
- Estimate builds a full **~11-table owned catalog schema**; confirmed architecture's Application DB is explicitly narrow (identity mapping, a read-only Catalog Read Model, import job/log status) — catalog data itself lives in Bitrix24.
- Estimate has an **image upload/serving module**; confirmed architecture states images are Bitrix24-hosted URL references — no object storage needed.

This is not reconcilable as a relabeling exercise — it would require rewriting the majority of the estimate's line items around a different integration target (Bitrix24 REST/webhooks) rather than around owned CRUD/persistence. On size: it's genuinely unclear whether the Bitrix24-centric version is larger or smaller in raw hours — a lot of the estimate's ownership work (custom RBAC, cart persistence, order tables, Stripe, image hosting) simply disappears, but it is replaced by integration work that isn't cheap either (webhook-driven sync + periodic reconciliation, catalog_id-parameterized dual-catalog sync, Bitrix24 CRM/Payment API integration, rate-limit-aware read-model design) — none of which appears anywhere in the estimate. The honest characterization is: **differently shaped**, with a real risk of both wasted estimated hours (work that shouldn't be built) and unestimated hours (integration work that must be built but isn't priced at all).

### 3. Backend-relevant items required by the confirmed architecture with no corresponding line item at all

- **Bitrix24 webhook-driven + periodic reconciliation sync** (the Catalog Sync/Proxy) — the mechanism that keeps the Catalog Read Model current. No line item anywhere in the estimate.
- **catalog_id-parameterized sync for two independent Bitrix24 catalog entities** (Furniture, Building Materials) — the estimate's CSV/catalog modules treat catalog work as singular/undifferentiated; the dual-catalog, independent-schema design isn't reflected.
- **Bitrix24 identity/OAuth bridging** — registering/logging in against Bitrix24 contacts, plus Google OAuth specifically. Module 5 only covers custom JWT/password auth; Bitrix24 bridging and Google OAuth are both absent.
- **Bitrix24 CRM deal/order creation calls** — the Commerce Bridge's actual job. Module 7 assumes an owned order table instead; the Bitrix24-facing integration work isn't estimated anywhere.
- **Bitrix24 Payment API integration specifically** — a Bitrix24-equivalent of PaymentIntent creation/webhook handling/order-status updates. The estimate's only payment work (module 10) targets Stripe, so this is a true zero-coverage gap under the confirmed direction.
- **Catalog Read Model as a read-only projection + rate-limit-aware design** — building and maintaining a denormalized cache distinct from a system-of-record schema, specifically engineered to avoid hitting Bitrix24 API rate limits. Not addressed; modules 1/3 assume direct ownership instead.
- **Admin CRUD as passthrough-to-Bitrix24** — the actual mechanics of "manual CRUD writes go to Bitrix24, then read model syncs," as opposed to owned-DB CRUD.
- **Unified search across two independently-schemad catalogs (FR-7)** as a cross-catalog concern, not just single-catalog full-text search.

### 4. Not resolved here — requires an explicit decision

This analysis intentionally does not decide whether the estimate should be revised to match the confirmed Bitrix24-centric architecture, or whether the confirmed architecture itself should be reopened in light of what the estimate assumes. Both documents referenced (`ready_for_dev_docs/` Vision & Scope and Architecture Specification for `rumica-starter`) are finalized project artifacts; the estimate is an external input that conflicts with them in ways that need an explicit decision from the user before any document or estimate is edited.
