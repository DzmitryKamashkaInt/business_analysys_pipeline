### (c) Easy-to-miss behavioral gaps (the coarse-grained-module risk)

1. **FR-6/FR-10 — two catalogs, two independent attribute schemas, two CSV templates.** Module 1 ("~11 JPA entities") and module 2 ("CSV Parsing & Data Import," singular) read as a design for **one** undifferentiated product catalog, with JSONB custom props as the only nod to per-item flexibility. Nothing distinguishes "Furniture schema" from "Building Materials schema," and nothing mentions building/maintaining **two separate CSV templates**. Either a real gap or an unspecified implementation detail — worth confirming before the pricing is trusted.

2. **FR-7 vs. FR-8 — unified search but catalog-specific browse.** Module 9 ("Full-Text Search") is a single weighted search over name/article/description with no mention of aggregating two differently-shaped catalogs into one result set, nor of keeping category/filter UI catalog-specific. Reads as generic single-catalog search — the FR-7/FR-8 split isn't evidenced.

3. **FR-11 — mixed cart across two catalogs.** Module 6 never references catalogs at all. Whether this is a non-issue depends on the data model: if module 1's "~11 tables" models Furniture and Building Materials as two separate entity types (as FR-6 suggests it should), a mixed cart needs to reference two item types polymorphically — work invisible in module 6's 14 hours. If everything is one generic "product" table with JSONB attributes, mixed cart is trivial. The estimate doesn't say which — currently ambiguous, not confirmed either way.

4. **FR-14/UC-6 — item card attribute set must be per-catalog-schema.** Module 3's "full detail endpoint (matches UI)" is singular and generic. Doesn't demonstrate rendering Furniture attributes for Furniture items and Building Materials attributes for Building Materials items as two distinct shapes, as FR-14 explicitly requires.

5. **UC-5/UC-6 alternative scenarios are silently absent.** None of the following — explicitly required by the confirmed UCs — appear anywhere in the estimate: (a) placeholder graphic when an item has no images, (b) omitting blank/broken attribute fields rather than rendering them, (c) per-row success/failure reporting back to the admin after a CSV batch import. Small-sounding but real work with no visible allocation in modules 2, 3, or 4.

6. **UC-3's exclusion of curated design packs / planner items.** Checked explicitly — non-issue; nothing in the 15 items reintroduces pack/planner-adjacent cart logic.

### (d) BR-4 — requires a rewording/retirement decision, not a coverage verdict

BR-4 as currently worded is "centralize commerce, CRM, and catalog operations in Bitrix24 — fully satisfied by Starter." Under this hypothetical (custom backend owning its own catalog/identity/orders), the BR's literal text no longer describes what the system would do — it isn't "satisfied" or "not satisfied," it's **factually inapplicable as written**. If this hypothetical were ever adopted for real, BR-4 itself would need to be reworded or retired in the Vision & Scope document.

### (e) Possible scope creep beyond the confirmed FR/UC set (independent of backend choice)

- **Module 5 — "role hierarchy (Admin/Editor/Viewer)."** The confirmed set names exactly one privileged role: **Admin** (UC-5, FR-9). "Editor" and "Viewer" appear nowhere in the confirmed documents — an unconfirmed addition regardless of backend choice.
- **Module 11 — "Stock Management"** (stock_quantity, decrement on paid order, out-of-stock handling). Inventory/stock tracking is not mentioned anywhere in BR-1..BR-5, FR-1..FR-14, or UC-1..UC-6. An entire 8-hour line item with no traceable requirement behind it.
- **Module 6 — guest cart + cart-merge-on-login.** UC-3 (purchase) requires a logged-in user as a precondition; nothing in the confirmed scope calls for a persistent guest cart that later merges into an authenticated one. May be reasonable elaboration, but not traceable to a stated requirement.
- **Module 2/3 — "category hierarchy" and "breadcrumb builder."** FR-8 only requires that category browsing/filtering stay catalog-specific; it doesn't specify a nested/hierarchical category structure or breadcrumb navigation. Likely low-risk elaboration, but flagged since not explicitly confirmed.
