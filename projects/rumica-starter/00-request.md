# Project Request — Rumica Starter (Phase 1 of `artdecor-home-design`)

## Original Request
Analyze how the full Rumica MVP scope (from the `artdecor-home-design` project) can be trimmed down to a starter/Phase-1 version covering: **catalogs (furniture AND building materials — the latter is a new addition, not in the original scope), user account/login, and product ordering** — while preserving a clear path to add the remaining previously-scoped features (2D planner, floor-plan recognition, galleries, favorites, subscriptions, admin panel, analytics) in later phases.

This is run as its own project (slug `rumica-starter`) because it is a materially different, smaller deliverable (Phase 1) derived from the already-finalized `artdecor-home-design` Vision & Scope and Architecture Specification — not a rework of that finalized MVP scope itself. The full MVP documents remain untouched in `projects/artdecor-home-design/ready_for_dev_docs/` as the target for later phases.

## Source Context (carried over from the parent project)

**Parent project:** `projects/artdecor-home-design/` — finalized Vision & Scope + Architecture Specification (Bitrix24-centric thin-bridge architecture), plus ad hoc note `notes_20260824_122706.md` (starter-scope analysis, produced on request before this project was created).

**Parent Vision & Scope — Full Rumica MVP scope (for reference, not all of it carries into Starter):**
Purpose: web platform connecting home-interior planning with real, purchasable furniture/decor products — differentiator is direct in-platform purchase of items used in a design. Target users: B2C home-design enthusiasts (primary), design-minded professionals (secondary, same tiers), internal Admin staff.
Full MVP in-scope: auth (email/password + Google OAuth), Free/Paid tiers, 2D room planner (Three.js), floor-plan upload+recognition+dimension-confirmation, Flat Plans gallery, public Design Projects gallery (publish/duplicate), product catalog (browse/search/filter/detail/"place in interior"), Favorites, Admin catalog CRUD (manual+CSV+pricing/priority), project management (save/duplicate/export/share/publish), cart+custom checkout form→Bitrix24 Payment APIs, subscription payment via Bitrix24-hosted flow, "My Orders" (Bitrix24 CRM), Admin panel (dashboard/user mgmt/moderation/reports), analytics (internal+GA/Mixpanel), transactional email.
Full MVP Business Requirements: BR-1 (non-specialists plan+furnish with real products), BR-2 (direct purchase from a design — core differentiator), BR-3 (freemium growth model), BR-4 (centralize commerce/CRM/catalog in Bitrix24), BR-5 (community/publish loop).
Parent architecture direction: Bitrix24-centric — Bitrix24 hosts admin/catalog/CRM/payments; thin custom bridge layer (API Gateway/BFF, Auth Bridge, Commerce Bridge with two distinct payment paths, Catalog Sync/Proxy — webhook + periodic reconciliation cache due to Bitrix24 standard-plan API limits, Projects Service with its own DB+Object Storage, Plan Recognition Adapter, Export Service, Analytics Forwarder).

## Already-Resolved Decisions (from ad hoc analysis + explicit user confirmation) — authoritative, do not re-ask

1. **Building materials catalog — CONFIRMED as a separate catalog** with its own attribute schema, not a category/filter within a single shared furniture catalog.
2. **Curated design packs — deferred.** Starter checkout covers individual products only, from either catalog. Design packs are out of Starter scope entirely (tied to the planner, which is also deferred).
3. **CSV import for catalog seeding — required from day one**, not optional/manual-only.
4. **Starter functional scope carried forward from the parent project's finalized FRs/UCs** (see full mapping in the parent project's `notes_20260824_122706.md`):
   - Carried into Starter (adapted where noted): FR-1, FR-2, FR-3 (auth, unchanged); FR-4-starter (profile, simplified — no tier visibility); FR-13-starter (catalog browse/search/filter — **now spans two independent catalogs**, furniture and building materials, each with its own attribute schema); FR-15-starter (Admin catalog CRUD, manual entry **and CSV import from day one**, for both catalogs; pricing/priority rules deferred); FR-20 (cart + custom Rumica checkout form → Bitrix24 Payment APIs, unchanged); FR-22 (My Orders from Bitrix24 CRM, unchanged).
   - Use cases carried into Starter: UC-1 (register/login, unchanged); UC-6-starter (purchase — **individual products only**, from either catalog; no design packs); UC-7 (My Orders, unchanged); UC-9-starter (Admin — catalog seeding/CRUD for both catalogs only, no user management/moderation/reports).
5. **Explicitly deferred to a later phase** (not deleted, not "Post-MVP" in the original sense — just out of Starter, to be re-added in a future phase without rework of what Starter builds): 2D Room Planner (FR-6–FR-10, UC-2, UC-4), floor-plan upload/recognition, Flat Plans gallery (FR-11), public Design Projects gallery/publish/duplicate (FR-12, FR-19, UC-3, UC-5 in part), Project management/save/duplicate/export/share (FR-17–FR-19, UC-5), Favorites (FR-16, UC-10), Free/Paid subscription tiers and their limits (FR-5), subscription checkout path (FR-21, UC-8), full Admin panel beyond catalog CRUD (FR-23–FR-26), analytics integration (FR-27).
6. **Business-requirement tension — carry forward as a known, accepted limitation, not to be silently resolved:** a catalogs+account+ordering Starter does NOT satisfy BR-2 (purchase *from a design* — Rumica's core differentiator) or BR-5 (community/publish loop) — both depend entirely on the deferred planner. BR-1 is only partially met (no "plan" capability in Starter). BR-3 (freemium) does not apply to Starter (no tiers). Only BR-4 (Bitrix24 centralization) is fully satisfied by Starter. This should be stated plainly in the Starter Vision & Scope's Purpose/Business Requirements section, not hidden.
7. **Architecture direction:** Starter must remain Bitrix24-centric, consistent with the parent project — no new backend paradigm. **Open question for the system-architect step (Step 4 of this pipeline run, not pre-decided here):** given building materials is now confirmed as a genuinely separate catalog with its own attribute schema (not a shared-schema category/filter), should this be modeled as (a) two catalog entities within Bitrix24 (each with its own property set), or (b) some other Bitrix24-native multi-catalog mechanism; and whether the existing Catalog Sync/Proxy design (webhook + periodic reconciliation cache) generalizes to two catalogs via parameterization, or needs two parallel sync pipelines feeding a common or separate front-end read model. This is a real architectural decision to be made during the architecture step, not assumed by this request document.

## Q&A Transcript
(To be appended by the orchestrating agent as the business-analyst's and system-architect's clarifying questions — if any remain beyond what's already resolved above — are answered.)

**Q:** [Discovery] With furniture and building materials as two independent catalogs (each with its own attribute schema), should Starter provide a single unified search/browse across both, or fully separate storefront sections with no cross-catalog search? → **A:** Unified search bar across both catalogs; category browsing/filtering stays catalog-specific (separate browse sections).

**Q:** [Discovery] Since the two catalogs have distinct attribute schemas, should CSV import use one template per catalog, or a single unified template? → **A:** Two separate CSV templates — one for furniture, one for building materials, each matching that catalog's own attribute schema.

**Q:** [Discovery] Should Admin catalog management (FR-15-starter, UC-9-starter) be a single unified admin screen with a catalog-type switcher, or two separate admin sections? → **A:** Unified — one "Catalog Management" screen with a toggle between Furniture and Building Materials, shared CRUD + CSV import UI pattern.

**Q:** [Discovery] Can a single cart/order contain items from both catalogs at once, or must furniture and building materials be ordered separately? → **A:** Mixed cart allowed — one cart, one checkout, one Bitrix24 order can contain items from both catalogs together.

**Q:** [Discovery] Is there an expected initial/near-term scale for the two catalogs that Starter's CSV import and browse/filter UX should be designed around? → **A:** Medium (low thousands of SKUs per catalog) — import should support batch/async processing; listing needs solid pagination and indexed filtering.
